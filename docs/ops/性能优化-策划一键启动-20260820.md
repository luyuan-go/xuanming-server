# 性能优化：策划免 Docker 一键启动（2026-08-20）

## 1. 结论

本轮把 `策划一键启动-免Docker-测试版.cmd` 的日常路径收敛为“强指纹判变化，只做必要工作”：

- 第三方包整套安装收据命中后，不再逐目录、逐文件检查；首次安装、版本或固定 SHA256 变化才备料。
- 策划表输入与生成器均未变化时，以 SHA256 指纹跳过导表；任一输入变化仍正常导表。该优化对所有
  `-GenTables` 启动模式生效。
- MySQL init SQL 的强指纹、MySQL `server_uuid`、`datadir` 和 84 张表库存均一致时，跳过重复 DDL；
  正式 migration 校验仍每次执行。
- 业务服务按真实 Go 依赖闭包建立逐 build-target 强指纹；输入与本地 EXE/运行收据一致时不执行
  `go build`，只变一个依赖闭包就只更新对应实例。22 个运行实例对应 21 个唯一构建目标：
  `matchmaker` / `matchmaker_pve` 共用一次构建并一起切换。服务按非 login / login 两波启动，并以
  共享 listener 快照验证 exact PID。
- 已安装且已初始化的本机基础设施在策划 fast 标志下先批量拉起，再统一等待；首次安装、`-Force`、
  收据缺失或初始化缺失仍走原串行路径。

最早的分钟级主因之一确实是重复调用 `Get-NetTCPConnection`。这条 Windows CIM 查询在样本机单次
约 4 秒，22 个服务的清端口、MySQL 归属检查和 ready 归属检查累计约 68 次，足以解释早期约
260 秒的业务服务阶段。该查询已换成一次 `netstat.exe -ano` 快照并复用。

已把 listener/PID 查询收敛到 `tools/scripts/lib/local_infra_state.ps1` 的共享实现，改用系统目录下
的 `netstat.exe -ano` 单次快照；`run_services.ps1`、`local_infra.ps1`、迁移归属复核和
`start.ps1` 的本机边缘端口预检全部复用，并保留 fail-closed 与 exact owner 校验。第三方 SVN bundle 则在
固定 SHA256 通过后直接只读解包，不再先复制到 `run/localinfra/cache`。

本轮没有把 22 个业务 EXE 临时改成单一压缩包。压缩只减少传输体积，不能消除首次 Windows PE
扫描与进程加载，而且会改变发布、manifest、运行目录、版本切换和回滚边界。

## 3. 修复与不变量

共享 seam 包含：

- `ConvertFrom-PandoraNetstatTcpListeners`：只接受 TCP `LISTENING` 行，解析 IPv4/IPv6，过滤
  UDP、PID 0、邻近端口并去重。
- `Invoke-PandoraNetstatTcpSnapshot`：只执行 Windows System 目录下的 `netstat.exe -ano`，
  不信任 PATH 同名程序；不能使用会漏掉 TCPv6 的 `-p tcp`。
- `Get-PandoraTcpListenerProcessIds`：命令非零、无可验证 TCP/listener 行或格式异常都抛错。

调用方保持以下安全不变量：

- ready 只接受 listener PID 等于本次启动进程 PID；端口“能连”不能冒充服务已就绪。
- 残留端口只停止映像路径等于本 release exact exe 的进程；路径不可读、外部同名程序、Docker
  proxy 都不猜、不杀。
- MySQL 仍同时核对状态 PID、`mysqld.exe` 路径、命令行 `--defaults-file` 指向本工作区
  `my.ini`，以及 listener PID；任一查询未知都拒绝迁移/复用。
- 并发只改变“先全部 launch、再统一 wait”的编排，不删检查、不缩短全局 deadline；login 必须在
  非 login 波全部 exact-ready 后才启动。
- 已存在进程、端口刚出现、错误 PID 抢端口、进程秒退、listener 查询失败和同步期输入变化均
  fail-closed，不能把“进程存活”或“端口可连”冒充服务已就绪。
- MySQL init 收据绑定同一 `server_uuid + datadir + 文件强哈希 + 实际库表库存`；重建数据目录、
  SQL 新增/删除/改名/改内容或表缺失都会回退完整回放。
- 基础设施并发仅在策划标志、安装收据已存在、MySQL/Kafka 已初始化且非 `-Force` 时启用；Kafka
  同时验证 broker/controller 两端口由本轮 cmd 的 exact Java 子进程持有。
- 重复双击不要求先停止：未变化且健康的进程保持原 PID；变化目标先在 staging 完成构建和二次输入
  稳定校验，再停止旧实例并发布，编译失败不能先打掉当前可用环境。重启电脑后进程全缺失时复用
  有效安装/构建收据，只执行缺失进程 launch + readiness。
- 标准 `Press any key to continue` 已升级为玩家可玩性契约：只有 exact login listener、经 8443
  实际到达 login upstream 的 Envoy 路由和 exact Hub DS UDP listener 全部通过后才显示；失败窗口
  保留非零退出码且不显示同一句成功提示。

## 4. 首次 SVN 更新与解包 I/O

7 个第三方包合计 570,950,631 字节（544.50 MiB），本身已经是 ZIP/TGZ/EXE：

- 再套 GZip 的实测为 544.49 → 538.51 MiB，只省 5.98 MiB（1.098%），不采用。
- SVN 工作副本内的 bundle 逐文件校验固定 SHA256 后直接读源文件解包；PowerShell bootstrap
  也直接读本机 bundle。这样不会再把同一批 544.50 MiB 复制到 cache。
- 显式 UNC/移动盘镜像与公网来源仍先复制/下载到本机 cache，避免网络中断时从远端边读边解。
- `run/localinfra/dist` 的包身份用 `.pandora-package.sha256` 绑定；缺 marker/版本变化会 staging
  重备，失败保留旧目录，不能靠复用旧二进制掩盖更新。

1. `services.zip` 只包含 22 个服务；`configtable-gen.exe` 与 `pandora-migrate.exe` 保持独立，
   不改变导表和迁移先后顺序。

## 8. 现场 35.63 秒样本与 Countdown 启动模型

### 8.1 样本与根因

用户 2026-08-20 提供的冷启动样本为 **35.63 秒**：基础设施总计 9.73 秒、数据库结构 0.92 秒、
业务程序 12.42 秒、业务阶段结束后继续等待 DS 11.45 秒。其中 MySQL/Redis/Kafka/Envoy 单项分别为
9.36/9.13/8.80/8.45 秒，而基础设施总计只有 9.73 秒，已经证明这一批是并行启动并统一等待；
单项耗时不能相加。

该样本并未连接远端数据库。现场缺少 `installers/planner-db/central-mysql.json`、公开 CA、runtime
profile 和 workspace identity，applied state 明确为 `local-owned/nodocker/:13307`，所以本机 MySQL
确实被启动。最终模式选择规则是：从未登记远端且缺 bundle 时立即 `local-owned`；bundle 存在或
已有 central applied/profile/identity 后锁定 `central-managed`，远端失败不回落。这避免中心尚未部署
时阻断策划，又防止已经写过远端数据的机器断网后切进另一套本机数据。

业务“配置生成”7.57 秒的直接原因也已定位：`Get-ServiceConfigPath` 为每个服务重复调用一次
`Assert-NoDockerMysqlOwned`，后者会做昂贵的 mysqld CIM/PID/命令行/listener 归属复核。脚本入口和
整批依赖探活本来已经各做一次 exact 检查；现已删除 22 次重复调用，并用 AST 契约锁定全脚本只保留
两次检查。远端 bundle 尚未部署，因而本轮不能给出新的完整冷启动 E2E 数字；不得把理论节省冒充实测。

自动回落修正后的真实无导表验证已进入 `local-owned`：基础设施 9.59 秒，MySQL/Redis/Kafka/Envoy
全部 ready，十库 migration/验收 1.18 秒全绿。随后业务 build 运行 38.60 秒时检测到仓库 Go/proto
输入仍被另一任务修改，二次强指纹按设计中止，未发布、未拉起任何业务进程；因此该轮 51.22 秒失败
样本不能用于评价配置生成优化。正式 CMD 同时被策划源表
`角色/j_角色等级.xlsx` 第 32 行“击杀经验”为空阻断，旧 dist 保持原子不变。

### 8.2 正确的并行边界

并行模型不是“所有步骤同时开始”，而是按依赖 DAG 分波 launch，再用共享 deadline/countdown 等待：

1. bundle/profile/TLS/workspace 先验证；失败时不得启动任何本机组件或业务进程。
2. Redis、Kafka、Envoy 属于同一基础设施波：全部 launch 后统一轮询，墙钟接近最慢组件。
3. 非 login 的业务服务属于第一波：全部 launch 后每轮只取一次 listener 快照，所有服务共享 12 秒
   deadline；`hub_allocator` 很早就启动，并在后台拉起、加载 Hub DS。
4. login 必须等第一波 exact-ready 后再启动，避免把未就绪依赖冒充可登录。
5. 最终绿灯同时要求全部业务 listener、Envoy Login 路由和 exact Hub DS UDP listener；任一退出、
   错 PID 抢端口或超时都 fail-closed。

因此同一波总时长应接近该波最慢任务，但完整总时长等于 DAG 的**最长关键路径**，不是全局所有任务的
最大值。日志里的“等待本机 DS 可玩 11.45 秒”只是业务波结束后剩余的 DS 加载尾巴；DS 已在
`hub_allocator` 启动后后台加载，不能再把 12.42 + 11.45 当成完全没有重叠的两次工作。

现有虚拟时钟契约已经验证：22 个服务 readiness 为 400 ms，而串行逐服务模型会是 8800 ms；
非 login + login 两波总计 800 ms，并且 timeout 不乘服务数量。下一轮真实远端冷启动需要连续采三次，
同时记录 `hub_allocator` 拉起、Hub DS 进程出现和 UDP ready 的时间戳；只有这样才能判断剩余关键路径
在 Kafka、远端预检还是 UE 关卡/DDC 加载。

场景：B 已有 199 个好友，上限 200。T1 接受 A→B，T2 接受 B→C，几乎同时。

根因：TiDB 悲观事务没有 gap 锁，`COUNT FOR UPDATE` 只锁已存在的行，锁不住「间隙里将要被 INSERT 的新边」。

✗ 不锁 player 守卫（裸 COUNT FOR UPDATE）→ 上限被穿透
T1：COUNT → 读到 199（<200 ✅）→ INSERT A→B
T2：COUNT → 也读到 199（<200 ✅）→ INSERT B→C
结果：B 的好友数 = 201 > 200，超限。两笔都「看见 199」，COUNT 锁住的都是已存在的旧边，新边插进间隙不受影响 → 幻读穿透
✓ 先锁 player(B) 守卫，再在锁内 COUNT → 上限权威
T1：锁 player(B) 守卫 → COUNT 199 → INSERT A→B → COMMIT 释放（B 变 200）
T2：等 player(B) 守卫…拿到后 → COUNT 200（≥200 ❌）→ 拒绝 B→C
结果：T1、T2 抢同一行守卫锁 → 串行。T2 的 COUNT 必然读到 T1 提交后的最新值 → 不超限

守卫行（friend_player_guards）是一行永远存在的数据，对它做 `INSERT … ON DUPLICATE KEY UPDATE` 加的是真正的排他点锁——所有碰 B 的写都得先抢到这行锁。串行临界区内 COUNT 读到的必是「前一事务提交后」的结果，上限因此权威。
